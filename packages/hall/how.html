How it's built

Fast web 3D, with the numbers

Events in, a living world out: Guildhall turns event streams (coding agents, GitHub, a repo's history or your own) into a living island, drawn with three.js in your browser. It is also a place to push web 3D and measure what each idea is worth. This page walks through what we built, what it cost, and what went wrong. Every section ends in a link that opens the thing it describes.

  • 300adventurers on one island
  • 175 fpsuncapped, up from 51
  • 143draw calls, down from 1,226

How we measure: a production build in Chrome on a MacBook, uncapped (no vsync) at pixel density 2, High quality, medians of interleaved rounds. 60 fps is the bar. Uncapped numbers above it are headroom: how much room a feature leaves, not whether it ships.

I

Crowds: 300 adventurers

Every adventurer is a skinned character with its own skeleton, a mixer playing its clips, a name chip and a handful of meshes. At 13 that is cheap. At 300 it was 51 fps with 1,226 draw calls, and the slowest frames took 28 ms. Skinned meshes can't be batched like furniture, because every skeleton is different. So the crowd stopped being 300 characters and became one.

What did it

  • One bone texture for everyone

    Every clip of the shared rig is sampled once at load into a single texture. Per bone and frame it stores a turn and a scale about a fixed pivot, plus where that pivot is now: two texels. The vertex shader reads it, and crossfades two clips on the GPU. No mixer, no skeleton upload per character.

  • Simpler meshes, made at load

    meshoptimizer gives each body part two simplified index buffers, at half and a quarter of the triangles, sharing the same vertices and skin weights. About 39 ms once, in a lazy 19 KB chunk. Each member picks a level by its height on screen.

  • One shared label layer

    Name chips used to be one DOM element per adventurer, each repositioned every frame. Now they are one layer, drawn together, and they fold away when they would crowd each other.

  • Hidden models leave the scene

    A model that isn't showing is parked out of the scene graph, not just made invisible, so three doesn't walk it, sort it or update its matrices each frame.

  • One upload a frame

    Where each member stands, faces, which clip it plays and its tint all go into one data texture, uploaded once a frame, instead of many instance buffers updated one by one.

  • Heroes up close

    Whoever you select, whoever is near and large on screen, keeps a full skinned body. The brain is shared, so a member swaps between the two with its pose carried exactly. Up to 16 adventurers, nothing changes at all.

One detail worth stealing: blending two baked frames by lerping whole matrices put a vertex up to 5 cm off. Storing the motion as a turn about a pivot and blending that instead stays close to what the mixer would draw, and a test holds it there.

Try it ?story=rush&n=300

Any crowd from 1 to 500. Settings › Stats for nerds shows frame rate and draw calls live.

II

WebGL against WebGPU, honestly

WebGPU is faster, and also not a free switch. The hall can run on either: WebGL stays the default, and Settings › Renderer switches to WebGPU where the browser has it. The shaders are being moved to TSL, three.js's node language, so one description of a material compiles to GLSL for WebGL and WGSL for WebGPU.

The catch was batching. The island's static pieces live in BatchedMeshes, which on WebGL draw many objects in one call with multi-draw. WebGPU in three.js has no multi-draw yet, so the same batches fell apart into one draw call per piece: about 1,000 calls at a normal view. The fix on WebGPU is to bake each static batch into one merged mesh per material at load. WebGL keeps its own path.

Try it ?story=rush&n=300&renderer=webgpu

Or open Settings › Renderer in the hall. Needs a browser with WebGPU; it falls back to WebGL otherwise. The 1,000-adventurer lab runs from a checkout: bun run dev, then ?lab=crowd&n=1000&renderer=webgpu.

III

TSL on WebGL: the gotchas

Running node materials on the WebGL renderer is the gentle way into WebGPU: port a shader, check it pixel for pixel against the GLSL, move on. It mostly works. These five did not.

  1. Uniform blocks run out

    Symptom
    With 300 adventurers on node materials, some of the crowd drew black.
    Cause
    On WebGL each node material declared its own object and render uniform blocks. ANGLE on Metal (Chrome on a Mac) has 32 binding points, and the crowd used them all.
    Fix
    Declare those groups as plain uniforms, uploaded per draw: 32 bindings down to 1–2.

  2. Double sRGB inside render targets

    Symptom
    Node materials drawn into the post chain came out too light.
    Cause
    The node output step tone-mapped and encoded colour inside the composer's buffer, and the post chain encoded it again on the way out.
    Fix
    Do nothing in a render target; tone-map and encode only on the canvas, the way the built-in WebGL materials do.

  3. Fog in the wrong colour space

    Symptom
    Node fog was darker than the GLSL fog on WebGL, and lighter on WebGPU.
    Cause
    The fog colour was mixed in before converting it to the output colour space.
    Fix
    Convert fog.color first and fog last, as the built-ins do. Full fog now matches GLSL exactly.

  4. Swapped textures never reach WebGPU

    Symptom
    The water's baked shoreline, set after the material was built, never showed on WebGPU.
    Cause
    Assigning a new texture to a node material that was already built works on WebGL, but WebGPU keeps the binding it made the first time.
    Fix
    Build the material without the texture, then build it once more when the bake lands.

  5. .toVar() before the first branch

    Symptom
    A value read inside an If and again after it came out unset after it.
    Cause
    A node is emitted where it is first used. First used inside a branch, it only exists there.
    Fix
    Anything read both inside and outside a branch becomes a .toVar() before the first one.

IV

Repos as islands

The guild's home is a hand-drawn hex map. Any other repo grows its own island from its file tree: two calls to GitHub's public API, then a planner that works hex by hex. The same repo always grows the same island.

The archipelago puts several repos on one sea, in a ring round the guild's own island. A map view names each island in its language's colour, the camera flies between them, and ferries cross on the story clock. Far islands drop their grass and small plants, and the map view draws in 58 to 66 calls. The public site uses trees fetched once, so it makes no API calls of its own.

Try it ?repo=facebook/react ?archipelago

Swap in any public owner/name. In the archipelago, press M for the map.

V

GitHub as a sea

When a project's remote is on GitHub, the water round its island fills with it. Commits and pull requests sail in as ships. The lighthouse burns steady while CI passes and pulses red when it fails. A release arrives as a galleon.

  • Every request is conditional. The hub sends the last ETag, and a 304 Not Modified costs nothing against the rate limit.
  • Gentle by default. A repo is asked at most once a minute with a token, every ten minutes without. A quiet repo is asked less and less often, a failing one backs off to fifteen minutes, and the hub stops before the hourly limit runs out.
  • The token never leaves the hub. It is the GitHub CLI's own, read when it's first needed, held in memory, and sent only in the Authorization header to api.github.com. It is never logged, written down or passed to the hall.
  • Nothing old is announced. The first look at a repo is a baseline. Only what happens after it sails in.
Try it ?story=seas

A simulated party's run with its sea beside it, from the first push to the release.

VI

How we know it still works

A 3D scene can break without a single test going red: a light turns off, a shader goes black, the fog shifts a shade. So the rule is to look at real rendered pixels, but only as many as a change needs.

  • Golden views

    24 reference shots, each a deep link with the story paused at a fixed moment, a fixed hour and weather, quality pinned and the camera framed. A paused build pins the render clock, so wind, sails, grass and water draw the same frame on every load. A check diffs each view and flags clusters of change, not lone noisy pixels.

  • A warm probe

    A browser kept running beside the dev server. A shot costs about a second, against about eighteen for a cold launch, so looking is cheap enough to do every time.

  • Labs

    One thing alone, without the island: a character playing one clip, one prop, one event, a crowd of a thousand. They load in about a second and isolate the thing being changed.

  • Bundled A/B

    A visual pass is measured as one comparison, everything on against everything off, on a production build, in interleaved rounds with paired medians. It is broken down feature by feature only when the bundle is over budget.

The numbers on this page come from a laptop that was usually doing other work too. That is why they are reported as ranges and paired differences, and why the interesting reading is the step, not the absolute.

Try it ?story=saga&t=6:00&hour=18.5&weather=clear&look=island

The same kind of deep link the golden views are made of: a moment, an hour, a camera.
